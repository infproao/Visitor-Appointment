## 二、根因（不是"没看清"，是流程缺环）

1. **节点没定位就开始写**。`LanguagePopup` 在注册表里长期写「无确认 Figma 节点」，实际它在「越南版-用户端 > 越南版访客预约填报 > 切换语言」`4:4202`，一直存在。没定位 → 只能按 `Select List` 类推 → 标题文案、上下 padding、按钮尺寸全部带偏差。
2. **只做统计，不做逐属性核对**。规范阶段统计的是全文件高频值（字号集合、间距集合、圆角集合），这能保证"取值不越界"，但保证不了"某个组件这一行是 44 还是 48、padding 是 8 还是 16"。
3. **用通用做法填空**。Vant 默认、常见移动端习惯（48 行高、8 左右 padding、列表加 1px 分割线、弹窗 `round` 16）被当成默认值写进组件，而不是去读节点。
4. **缺少比对环节**。没有做「Figma 导出图 ↔ 实现截图」的并排/叠图核对，只在最后量了几个关键尺寸，偏差就漏过去了。
5. **变量 API 403**。`/variables/local` 等接口无权限，拿不到变量名和模式值；颜色名、间距 token 名只能从画板文字标注推断，命名类信息天然不可靠（不影响数值，但影响"这个值属于哪个 token"的判断）。
6. **状态没有闭环**。20 个组件全部 `pending`，`pendingNote` 靠人工记，没有逐项截图签收。
7. **颜色从截图取色，没回 Figma / token 对照**（2026-11-09 用户「按钮颜色是 22BBB3，5AB9B2 是哪生成的」）。`Button` 的 5 个色系是拿用户给的变体截图逐格取色写死的，teal 取成 `#5AB9B2`，与 Figma 实测 `#22BBB3`（84 处）差 47 个色阶，而这个值在 token、SVG 导出、Figma 节点里**都不存在**——说明取色环节本身不可靠（截图压缩 / 缩放 / 色彩管理都会偏）。**颜色一律以 token 或 Figma 节点 fill 为准，截图只能用来确认「有哪些变体」，不能用来定色值。**

## 五、固定流程（每个组件都要走完）

1. **先定位节点**：在全文件（11 个 CANVAS、82,427 节点）按名称搜索，写出「所在页面 > 位置 > Figma 名称 + Node ID」；找不到就标「待确认」，**不允许**用相似组件代替。
2. **逐属性读**：尺寸、`padding*`、`itemSpacing`、`cornerRadius` / `rectangleCornerRadii`、`fills`、`strokes`、文字 `fontSize/lineHeightPx/fontWeight/fills`。禁止用 Vant 默认值填空。
3. **写实现**：CSS 值与第 2 步一一对应，注释里写下节点 ID。
4. **浏览器实测**：用 `getBoundingClientRect` + `getComputedStyle` 回读，与第 2 步逐项对齐（差值 > 1px 视为不通过）。
5. **登记**：把结果写回本文件第三节，注册表状态仍保持 `pending`，待设计方截图确认后再改 `confirmed`。
